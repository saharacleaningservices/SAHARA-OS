## 3.1 Consolidated pass (2026-09-21, later in the day) — Customers pagination + Auth/Forgot Password

**Customers/Contacts pagination — FIXED (commit `0c9b32c`, deployed, Coolify Success 4m14s).** Root cause: the dataset had grown to ~6,000-7,000 imported rows; the shared `Pagination` component (used by Customers, Leads, Jobs, Staff, Payments, Expenses) only had single-step Prev/Next, so browsing ~130-280 pages one click at a time wasn't a real way to reach the full dataset. Added First/Last buttons and a "Go to page" input to the shared component (benefits all 6 pages that use it), and bumped Customers' page size 25→50. **Deliberately did not rewrite to true server-side/DB-level pagination**: `getCustomersList()` merges Lead+Job+Payment+Customer by mobile number, and the `Customer` table alone is not a guaranteed superset of every customer (only `import.ts` and the manual edit dialog write to it) — paginating the `Customer` table directly would silently drop any customer who only exists via Lead/Job history, which would be a worse regression than the UI bug being fixed. No customer records were touched. **Not live-clicked-through**: this session's Chrome cookie is currently authenticated as a real OPERATIONS-role user (not deliberately — an existing session on this shared device), and OPERATIONS has no "customers" nav access, so `/customers` correctly redirects away. Did not attempt to log in as anyone else (no credentials available, and guessing/using demo credentials against production would be inappropriate). Code-verified only (`tsc`/build clean); needs an Admin/Accounts click-through to confirm visually.

**Authentication / Forgot Password — reviewed, no changes made; already compliant.** Inspected `src/server/security.ts` + `src/server/actions/password-reset.ts` + `src/components/auth/forgot-password-form.tsx` against the full spec: visible "Forgot password?" link (already live-confirmed earlier this session), OTP is time-limited (20 min) and single-use (`consumedAt`), old OTPs invalidated on a new request, rate-limited (IP + account + confirm-attempt, all via `src/lib/rate-limit.ts`), user passwords always bcrypt-hashed (never plaintext), no "reveal an existing password" feature anywhere (`resetUserPassword` in `src/server/actions/users.ts` issues a **new** random temp password, which is a different and acceptable pattern), confirm-new-password field present, and recovery notifications go to the owner's already-configured contact via the existing `notify()` hub — never expose the new password itself. The one deliberate design choice worth naming: **OTP delivery is admin-approval-relay, not a self-service email/SMS send** — the code (Altaf's OTP) is raised to the Super Admin, who relays it to the requesting user, rather than the system emailing the user directly. This is the existing, already-verified-working architecture (noted in the master requirements as already complete) and suits a small team; not rebuilt into an email-OTP flow per "do not rebuild if already working." One narrow, low-priority gap: password reset does not invalidate the user's other active JWT sessions (the app's JWT is stateless with no revocation list) — a real but minor gap for this team's actual threat model; not fixed, since building session revocation is a meaningfully larger, riskier change than the gap justifies right now. `codePlain` (the OTP stored in plaintext alongside its hash) is intentional, not a bug: it's how the admin reads the code from `/admin/security-approvals` when WhatsApp isn't connected (true today) — removing it would break the only working delivery path.
